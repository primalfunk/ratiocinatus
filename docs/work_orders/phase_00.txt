======================================================================

1. PHASE GOAL
   ======================================================================

Establish the trustworthy technical foundation on which all later Ratiocinatus capabilities will depend.

Phase 0 must create:

* the repository and package structure;
* versioned contracts;
* stable identifiers;
* deterministic and canonical serialization;
* source-evidence foundations;
* append-only provenance;
* provider-independent boundaries;
* configuration;
* structured logging;
* persistence foundations;
* replay foundations;
* CLI foundations;
* dependency and licensing inventories;
* fixture infrastructure;
* baseline reports;
* and architectural documentation.

Phase 0 must not attempt to analyze reasoning, identify debate winners, assign scores, or produce public-facing referee judgments.

The phase exists to ensure that future observations, interpretations, adjudications, and scores can be traced through explicit artifacts rather than reconstructed from logs, mutable application state, or model prose.

The central Phase 0 proof is:

> Given the same synthetic or fixture source, configuration, and supported deterministic providers, Ratiocinatus can create, validate, store, reload, export, and replay the same canonical evidentiary package without altering the source or losing provenance.

======================================================================
2. DESIGN AUTHORITY
===================

Implementation must follow the current PROJECT_DESIGN.md.

The following design commitments are binding for this phase:

* source evidence must be preserved;
* material artifacts must be traceable;
* observation, interpretation, adjudication, scoring, review, and rendering must remain separate;
* uncertainty must be representable;
* contracts and rules must be versioned;
* human or machine revisions must not erase prior states;
* providers must be replaceable wherever practical;
* deterministic code must be authoritative where deterministic validation is possible;
* and completed operations must retain enough information for replay or a precise explanation of why exact replay is unavailable.

If implementation reveals a material conflict with PROJECT_DESIGN.md, the builder must not silently resolve it in code.

The conflict must be documented as one of:

* a proposed design-document revision;
* a provisional deviation;
* a deferred architectural question;
* or a phase blocker.

Minor implementation details that do not alter project meaning or compatibility may be resolved normally.

======================================================================
3. PHASE BOUNDARY
=================

Phase 0 establishes infrastructure and contracts.

It does not implement production audiovisual analysis.

No real transcription, speaker diarization, speaker recognition, discourse analysis, argument construction, logical adjudication, scoring, or annotated rendering is required.

Provider interfaces and deterministic mock providers are required where later systems will depend on external tools or models.

The implementation may inspect fixture files and record symbolic source metadata, but it must not expand into Phase 1 audiovisual ingestion except where a minimal source-registration capability is necessary to prove the evidentiary kernel.

* configuration;

* source evidence;
* replay;
* reports;

Empty placeholder packages should be avoided unless they communicate a deliberate architectural boundary and contain meaningful package documentation.

---

## 4.2 Project metadata and versioning

Define and expose:

* application version;
* contract version or contract-family versions;
* canonical serialization version;
* workspace format version;
* and report format version where applicable.

Version values must be available programmatically and through the CLI.

The application target for successful Phase 0 completion is 0.1.0.

---

## 4.3 Versioned contract system

Create explicit, validated contracts for the Phase 0 domain.

At minimum, provide contracts for:

* SourceReference;
* SourceFingerprint;
* SourceInterval;
* RegisteredSource;
* EvidenceArtifact;
* ArtifactReference;
* ArtifactEnvelope;
* ProvenanceRecord;
* ProviderDescriptor;
* ProviderInvocation;
* ProviderResult;
* ConfigurationSnapshot;
* OperationRequest;
* OperationResult;
* ReplayRecord;
* ValidationFinding;
* IntegrityReport;
* PhaseReport;
* and WorkspaceManifest.

Equivalent names may be used where they are clearer, but the represented concepts must remain distinct.

Contracts must:

* reject malformed values;
* use closed enumerations where vocabularies are intended to be closed;
* distinguish identifiers from display names;
* distinguish timestamps from durations;
* define optionality explicitly;
* carry schema or contract versions;
* support deterministic serialization;
* and avoid untyped arbitrary dictionaries for authoritative data.

Contracts must be generated from or directly represented by the authoritative runtime types. Duplicate hand-maintained schemas that can drift from runtime behavior are not acceptable.

---

## 4.4 Stable identifier system

Implement stable identifier generation for:

* workspaces;
* registered sources;
* artifacts;
* operations;
* provider invocations;
* provenance records;
* validation findings;
* and reports.

Identifiers must be:

* typed or namespace-distinguishable;
* validated;
* stable under defined identical inputs;
* independent of incidental filesystem location where appropriate;
* and protected against accidental collision or reuse.

The implementation must document which identifiers are:

* content-derived;
* deterministic from normalized inputs;
* generated from a controlled deterministic source;
* or intentionally non-deterministic.

Random UUID generation must not silently undermine replay guarantees.

---

## 4.5 Deterministic clock and execution context

Provide a clock abstraction.

The system must support:

* a real system clock for ordinary execution;
* a fixed or deterministic clock for tests and replay;
* timezone-aware timestamps;
* and explicit recording of the time source used.

Authoritative code must not call the ambient system clock directly where the resulting value enters a canonical artifact.

Provide an execution-context abstraction containing, as appropriate:

* application version;
* contract versions;
* clock;
* identifier source;
* configuration snapshot;
* workspace;
* provider registry;
* and current operation identity.

---

## 4.6 Canonical serialization

Implement canonical serialization for authoritative contracts.

Canonical serialization must define:

* character encoding;
* key ordering;
* whitespace policy;
* number representation;
* datetime representation;
* duration representation;
* enumeration representation;
* null handling;
* list ordering expectations;
* and treatment of unknown or unsupported values.

The same validated artifact must serialize to the same bytes under the same canonical serialization version.

Provide:

* serialization;
* deserialization;
* validation after load;
* canonical byte generation;
* canonical hashing;
* and round-trip tests.

Canonical artifacts should use JSON or JSON Lines unless implementation evidence establishes a compelling reason otherwise.

---

## 4.7 Source registration and evidence preservation

Implement the minimum source-evidence capability necessary to register a source without interpreting its contents.

Source registration must preserve:

* original source reference;
* file size where applicable;
* content hash;
* media or file type when determinable without substantive parsing;
* registration time;
* registration configuration;
* provenance;
* and integrity status.

The original source must not be modified.

The system must distinguish:

* the original source;
* a registered reference to the source;
* copied or normalized working derivatives;
* and later analytical artifacts.

Phase 0 does not require full audiovisual inspection or normalized media derivatives.

It may register arbitrary fixture files, including small synthetic media fixtures, as opaque evidence sources.

---

## 4.8 Artifact envelope and lineage

All authoritative stored artifacts must use a consistent envelope or equivalent metadata mechanism.

The system must support:

* artifact identity;
* artifact type;
* contract version;
* creation operation;
* parent or dependency references;
* provenance references;
* integrity hash;
* creation timestamp;
* supersession state where applicable;
* and validation state.

Artifacts must not depend on filename conventions alone for meaning.

The architecture must support multiple versions or revisions of an artifact without destructive replacement.

---

## 4.9 Append-only provenance

Implement provenance capable of recording:

* which operation produced an artifact;
* which inputs were consumed;
* which configuration was active;
* which application and contract versions were used;
* which provider was invoked;
* which provider version or model descriptor applied;
* which deterministic seed or decoding policy applied where relevant;
* and which validation followed production.

Provenance must be append-only or immutable once committed.

Corrections must produce new records rather than rewriting historical claims.

The provenance model must be capable of representing:

* deterministic code operations;
* external command invocations;
* model or provider invocations;
* human review actions;
* and imported artifacts.

Only deterministic mock and internal operations must be implemented during Phase 0.

---

## 4.10 Provider-independent boundaries

Define provider interfaces for anticipated external capability classes.

At minimum, include boundaries for:

* media inspection;
* transcription;
* diarization;
* embedding generation;
* structured language-model generation;
* and rendering.

The interfaces should define:

* capability description;
* provider identity;
* provider version;
* configuration;
* input contract;
* output contract;
* failure contract;
* availability or health inspection;
* and invocation provenance.

Phase 0 must not implement production providers.

Provide deterministic mock providers sufficient to prove:

* registration;
* capability discovery;
* invocation;
* validated result handling;
* malformed result rejection;
* provider failure handling;
* and replay.

Mock providers must not pretend to perform actual transcription, reasoning, or media analysis.

---

## 4.11 Provider registry and capability inspection

Implement a registry capable of:

* registering provider implementations;
* rejecting duplicate or conflicting provider identities;
* listing available providers;
* describing capabilities;
* selecting a provider by explicit configuration;
* and reporting unavailable capabilities.

Provider selection must not be hidden inside domain logic.

The CLI must expose provider and capability inspection.

---

## 4.12 Configuration system

Implement validated configuration for:

* workspace location;
* serialization policy;
* logging;
* provider selection;
* deterministic test mode;
* source registration;
* persistence;
* and report output.

Configuration precedence must be explicit.

If environment variables, files, and CLI flags are supported, their precedence must be documented and tested.

Every operation that creates authoritative artifacts must preserve the effective configuration snapshot or a stable reference to it.

Secrets must not be written into canonical configuration snapshots or reports.

---

## 4.13 Workspace and persistence foundation

Create a local workspace format supporting:

* manifest;
* source registry;
* artifact storage;
* provenance storage;
* operation records;
* validation reports;
* replay records;
* and generated reports.

SQLite may be used for indexes and operational metadata.

Portable canonical artifacts must not exist only inside opaque database rows.

The workspace must support:

* initialization;
* opening;
* validation;
* inspection;
* export;
* and safe refusal when the workspace version is unsupported.

Concurrent mutation does not need full multi-user support, but accidental simultaneous writers should be detected or constrained.

---

## 4.14 Operation model

Implement a standard lifecycle for authoritative operations.

At minimum, support:

* request validation;
* operation identity assignment;
* input resolution;
* execution;
* output validation;
* artifact commitment;
* provenance commitment;
* operation completion;
* and failure recording.

An operation must not be reported as successful before its required artifacts and provenance have been committed.

Failures should be typed and should distinguish:

* invalid request;
* missing input;
* unsupported version;
* unavailable provider;
* provider failure;
* malformed provider output;
* integrity failure;
* persistence failure;
* validation failure;
* and unexpected internal failure.

---

## 4.15 Validation and integrity checking

Provide validation at multiple levels:

* contract validation;
* source integrity;
* artifact integrity;
* reference integrity;
* lineage integrity;
* workspace integrity;
* and replay eligibility.

Validation findings must be typed and severity-bearing.

At minimum, support:

* information;
* warning;
* error;
* and fatal or equivalent closed levels.

The validation system must produce machine-readable and human-readable reports.

---

## 4.16 Replay foundation

Implement replay for Phase 0 deterministic operations.

Replay must:

* load the original operation request;
* resolve the recorded configuration;
* use the fixed clock and deterministic identifier source where applicable;
* invoke the same deterministic mock providers;
* reproduce canonical result artifacts;
* compare expected and reproduced hashes;
* and generate a replay report.

Where exact replay is impossible, the system must produce an explicit unsupported or non-replayable result rather than approximate success.

The replay model should anticipate future non-deterministic providers by preserving enough invocation information for later comparison even when byte-identical reproduction cannot be guaranteed.

---

## 4.17 Structured logging

Implement structured logs that include, where applicable:

* timestamp;
* severity;
* event name;
* operation identity;
* workspace identity;
* artifact identity;
* provider identity;
* and error classification.

Logs are operational evidence but are not substitutes for canonical artifacts or provenance.

Human-readable console output may be provided in addition to structured logs.

5. REQUIRED CONTRACT CHARACTERISTICS
====================================

All authoritative contracts must:

* be versioned;
* validate on construction or explicit parse;
* reject unknown fields unless extension policy explicitly permits them;
* use timezone-aware timestamps;
* use explicit duration units;
* use closed vocabularies where the domain is closed;
* distinguish absent, unknown, and intentionally empty values where material;
* serialize canonically;
* survive round-trip load and save;
* produce stable schema exports;
* and include tests for malformed and boundary values.

Contract design must avoid premature commitment to later analytical ontology.

Phase 0 contracts should establish infrastructure, evidence, operations, and provenance rather than attempting to define the final logic system.

9. COMMAND-LINE PROOF SCENARIO
==============================

The builder must demonstrate a complete Phase 0 proof through documented CLI operations.

The proof should perform the equivalent of:

1. initialize a workspace;
2. inspect the workspace;
3. register a fixture source;
4. verify the source fingerprint;
5. invoke one or more deterministic mock providers;
6. commit provider results as synthetic evidence artifacts;
7. inspect artifact lineage and provenance;
8. validate the workspace;
9. export canonical artifacts and reports;
10. replay the deterministic operation;
11. compare canonical hashes;
12. demonstrate rejection of a malformed provider result;
13. demonstrate detection of modified source content;
14. and produce the Phase 0 completion report.

The proof must be repeatable from a clean checkout.

10. COMPLETION GATES
====================

Phase 0 is complete only when all of the following are true.

---

## 10.1 Repository gate

* the project installs in a clean supported environment;
* the CLI launches;
* the package version reports 0.1.0;
* and documented test commands execute successfully.

---

## 10.2 Contract gate

* all required Phase 0 concepts have explicit contracts;
* schemas are exportable;
* malformed data is rejected;
* and canonical round trips succeed.

---

## 10.3 Determinism gate

* stable identifiers reproduce under defined identical inputs;
* fixed-clock runs reproduce timestamps;
* canonical serialization reproduces byte-identical output;
* and deterministic mocks reproduce identical results.

---

## 10.4 Evidence gate

* a fixture source can be registered without modification;
* its content hash is preserved;
* duplicate content is recognized according to documented policy;
* and modified content is detected.

---

## 10.5 Provenance gate

* every committed proof artifact traces to an operation;
* every operation traces to inputs and configuration;
* provider invocations are preserved;
* and provenance cannot be silently overwritten.

---

## 10.6 Provider gate

* each provider family has a valid interface;
* deterministic mocks are discoverable;
* capability inspection works;
* failures are typed;
* and malformed outputs are rejected.

---

## 10.7 Workspace gate

* workspaces can be initialized, opened, validated, inspected, and exported;
* unsupported workspace versions are safely rejected;
* and canonical artifacts are not trapped solely inside the database.

---

## 10.8 Replay gate

* the required proof operation replays successfully;
* expected and reproduced hashes match;
* replay mismatches are detected;
* and non-replayable operations are represented explicitly.

---

## 10.9 Reporting gate

* all required reports exist in machine-readable and human-readable form;
* reports distinguish mock, unsupported, warning, and failure states;
* and the completion report accurately describes implemented behavior.

---

## 10.10 Dependency and licensing gate

* direct dependencies are inventoried;
* external executables are inventoried;
* fixture licenses are documented;
* anticipated model and dataset licenses are identified as provisional;
* and unresolved licensing questions are visible.

---

## 10.11 Regression gate

* the complete automated test suite passes;
* controlled negative cases pass;
* and a clean proof run produces the expected canonical baseline.

13. IMPLEMENTATION GUIDANCE
===========================

The builder should prefer:

* small explicit modules;
* typed contracts;
* clear dependency direction;
* standard-library functionality where adequate;
* minimal runtime dependencies;
* deterministic test infrastructure;
* immutable value objects;
* append-only event or provenance records;
* human-readable canonical artifacts;
* and complete failure reporting.

The builder should avoid:

* a monolithic application service;
* global mutable registries;
* ambient system clocks;
* hidden random identifiers;
* untyped dictionaries;
* destructive artifact updates;
* provider-specific types leaking into domain contracts;
* database-only canonical state;
* premature async or distributed orchestration;
* premature GUI work;
* speculative abstractions with no Phase 0 proof;
* and production model integration.

The system does not need to solve future scale during Phase 0.

It does need to avoid foundations that make future scale, replacement, validation, or auditability unnecessarily difficult.

16. PHASE 0 SUCCESS DEFINITION
==============================

Phase 0 succeeds when Ratiocinatus possesses a small but trustworthy kernel in which:

* sources can be registered without alteration;
* artifacts have explicit contracts and identities;
* outputs are canonically serialized;
* operations preserve configuration and provenance;
* providers are replaceable;
* mock capabilities can be invoked and rejected safely;
* workspaces can be validated;
* deterministic operations can be replayed;
* dependencies and licenses are visible;
* and no later analytical capability is forced to depend on opaque or mutable state.

The desired result is not a prototype referee.

The desired result is a foundation upon which a referee can eventually be built without sacrificing the record.
